## なぜそうしたか

| 判断 | 採用案 | 対案と外した理由 |
|---|---|---|
| ツール | Playwright | Cypress は利用数が Playwright の 1 割弱まで下がっている。Puppeteer はブラウザ操作のライブラリで、テストランナーではない |
| 置き場所 | 独立したワークスペース `e2e/` | `apps/web/e2e/`。E2E は API と DB も起動するので、web の配下に置くと責任の範囲がずれる |
| テスト対象の web | 本番ビルド（`vite build` → `vite preview`） | 開発サーバ。速いが、利用者が受け取るものとは違う。本番ビルドでだけ起きる不具合を拾えない |
| ポートと DB | web 4173 / API 3100 / `attendance_e2e` | 開発用と同じものを使う。開発中のサーバとぶつかり、開発データを壊す |
| DB の安全装置 | 名前が `_e2e` で終わらなければ起動を拒否 | api のテスト用（`_test`）と共用する。両方を同時に流すと互いの DB を作り直し合う |
| DB の準備 | `globalSetup` で api の `db:migrate` / `db:seed` を呼ぶ | **Playwright が現在推奨する「セットアップ用プロジェクト」**。ブラウザのログイン状態を作るような準備ならそちらが向くが、DB の作り直しはブラウザと無関係で、レポートやトレースに載せる利点がない |
| 起動済みサーバの扱い | 使い回さない（`reuseExistingServer: false`） | 使い回す。別の DB に繋がったサーバを掴むと、E2E 用 DB を作り直しても反映されない |
| ブラウザ | Chromium のみ | 3ブラウザ。CI の時間が約3倍になる。今の画面はブラウザ差の出る機能を使っていない |
| CI のブラウザ | 毎回ダウンロード | キャッシュする。**Playwright の公式が推奨していない**（復元とダウンロードの時間がほぼ同じで、OS の依存はキャッシュできない） |
| CI のジョブ構成 | `check` と並行の別ジョブ | 同じジョブで直列。ブラウザの準備分だけ待ち時間が伸びる |

## つまづき

ほとんど詰まらなかった。理由は、ここまでの STEP で作った仕組みをそのまま組み合わせられたため。

- DB を作り直す処理と名前によるガードは、STEP 03 の api のテストと同じ形
- API に別の DB を使わせる方法は、STEP 03 で確かめた「`loadEnvFile()` は既存の環境変数を上書きしない」がそのまま使えた
- 画面の振る舞いは STEP 05 でアプリ全体を描画してテスト済みだったので、実ブラウザで初めて見つかる差がなかった

小さなものは次の2つ。

| 事象 | 内容 | 対応 |
|---|---|---|
| 依存の追加時に非推奨の警告 | `@esbuild-kit/core-utils` / `@esbuild-kit/esm-loader` が非推奨。drizzle-kit が内部で使っているもので、今回の変更とは無関係 | 対応なし。drizzle-kit の更新で解消されるのを待つ |
| ダウンロードされたブラウザが arm64 版だった | **この Mac（Apple M4）の Node が Intel 用（x86_64）**で、Rosetta 経由で動いていた。Playwright はハードウェアを見て arm64 版を入れた | 動作に問題はない。ユーザーのマシンの設定なので変更していない（下記の申し送り） |

## 気づき・学び

**実ブラウザでしか確かめられない性質がある。**
MSW を使った画面のテストでは、Cookie の属性や、API そのものの防御は検証できない。E2E では次を確かめた。

- セッションの Cookie が `HttpOnly` / `SameSite=Lax` で発行され、**ページの JavaScript（`document.cookie`）から見えない**
- 画面を通さずに API を直接叩いても、未ログインなら 401、employee なら 403

後者は STEP 05 で書いた「画面側の権限チェックは UX、守りの本体は API」を実地で確かめたもの。

**E2E でも「壊して落ちる」を確かめた。**
`HttpOnly` を一時的に外すと、Cookie のテストだけが落ち、差分（`"httpOnly": true` → `false`）と失敗時のスクリーンショットが残った。

**安定性は複数回流して確かめる。**
2回続けて流して、9件とも通った（再試行なし）。E2E は不安定になりやすいので、最初に安定していることを確認しておくと、後で落ちたときに「テストが不安定なのか、コードが壊れたのか」を切り分けやすい。

**公式の推奨は、直感に反することがある。**
「CI ではブラウザをキャッシュした方が速い」と考えがちだが、Playwright の公式は推奨していない。理由まで読むと納得できた。

## 次への申し送り

- **E2E を走らせるには** `docker compose up -d` と、初回だけ `pnpm -F @attendance/e2e exec playwright install chromium` が必要
- **書き込みを伴う E2E（STEP 08 の打刻など）に注意。** 今の E2E は seed したデータを全テストで共有し、
  読み取りとログインしかしていないので並列に流せる。打刻のようにデータを書き換えるテストを足すときは、
  テストごとに別のユーザーを使うか、テスト内でデータを作るなどして、並列実行で干渉しないようにする
- E2E は主要な操作の流れに絞る。細かい分岐は MSW を使った画面のテストで確かめる（E2E は遅く、壊れやすいため）
- **この Mac の Node は Intel 用（x86_64）で、Rosetta 経由で動いている。** ネイティブ（arm64）の Node に入れ替えると、
  Node・esbuild・Biome などが速くなる。ユーザーのマシンの設定なので変更していない
