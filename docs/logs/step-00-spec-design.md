## なぜそうしたか

| 判断 | 採用案 | 対案と外した理由 |
|---|---|---|
| 打刻データの持ち方 | イベント列 (`time_entries`) を持ち、日次は導出 | `daily_records` に `start_at`/`end_at` を直接持つ案。実装は楽だが、修正申請の「どの打刻をどう変えるか」が表現できず、打刻漏れも表現できない |
| 勤務日の定義 | 出勤打刻の日付を `work_date` とする | ①暦日固定 → 深夜勤が2日に分裂し「1日の実働」が実務感覚とずれる ②起算5:00ルール → 実務的だが時刻→勤務日の変換関数が常に介在しテストが増える |
| 修正申請の粒度 | 日単位で一括 | 打刻1件ずつ申請する案。テーブルは単純になるが、「出勤と退勤を同時に直したい」が複数申請に割れ、部分承認で矛盾した状態が作れてしまう |
| 申請テーブルの構造 | ヘッダ (`requests`) と種別ごとの明細に分離 | ①種別ごとに完全分離 → 承認期限・代理承認・通知を種別が増えるたびに再実装することになる ②`requests` に全カラム → NULL 許容だらけになり型が緩む |
| 変更履歴の担保 | 変更経路を申請に一本化。`time_entries` の直接更新 API を作らない | ①`audit_logs` テーブルを別に持つ → ログの書き忘れが起きる ②`time_entries` を真の追記のみ (`superseded_by`) → 全クエリに「最新世代のみ」の絞り込みが必要になり、忘れると静かに壊れる |
| 認証 | 自前セッション (Cookie) | JWT は失効・リフレッシュの自前実装が必要。外部サービスは認証周りの学びが減る。学習目的に対して Cookie セッションが一番素直 |
| オリジン | web と API を常に同一オリジンにする | クロスオリジン + CORS + `SameSite=None` 案。設定が増える上に CSRF 対策を別途自前でやる羽目になる |
| 所定労働時間 | `users` に直接持つが、`getScheduleFor(userId, workDate)` 越しに引く | ①`work_patterns` マスタを最初から作る → Phase 1 には過剰 ②全社共通定数 → ユーザーごとの違いを表現できない。関数越しにすることで後から①へ差し替えられる |
| admin の扱い | 一般社員を兼ねる。ただし自己承認は 403 | 管理専用アカウント案。認可は単純になるが実務感覚からずれる。兼ねる方が「自己承認禁止」という認可ルールの練習にもなる |

## つまづき

設計段階なのでエラーではなく、**判断の誤りと見落とし**が中心。

| 事象 | 原因 | 解決 |
|---|---|---|
| 「退勤忘れは次回出勤時にブロックする」と決めかけた | 不正なデータを防ぐことばかり考え、ユーザーが何をしたいかを考えていなかった | ブロックしない方針に変更。打刻を成功させ、警告と修正申請への導線を出す |
| 「`time_entries` は追記のみ」と書いたのに、承認処理で `update`/`delete` する設計になっていた | 設計方針を書いた時点と、更新系の処理を書いた時点が離れていて、突き合わせていなかった | 変更経路を申請に一本化し、履歴は `requests` が持つと整理。`time_entries` は普通に更新する |
| セッション設計をほぼ書き終えてから、Cookie が飛ばない構成だと気づいた | Cookie の属性（`HttpOnly`/`SameSite`）だけ見ていて、web と API のオリジンが違うことを考慮していなかった | Vite の proxy で `/api` を API サーバへ転送し、同一オリジンに見せる方針に変更 |

### 退勤忘れの判断を覆した経緯

- **元の判断**: 前回の勤務が `clock_out` されていない状態で新規 `clock_in` が来たら 409 で拒否し、
  修正申請へ誘導する。不整合なデータが作られるのを未然に防げる。
- **覆した理由**: 月曜に出勤しようとして金曜の打刻漏れでブロックされると、**打刻そのものができない**。
  勤怠アプリとして本末転倒。データの正しさを守るために、アプリの一番の目的を犠牲にしていた。
- **新しい判断**: `clock_in` は常に受け付ける。レスポンスに未完了勤務の警告を含め、
  打刻画面と月次一覧で強調表示して修正申請へ誘導する。

## 気づき・学び

**状態を2箇所に持つと必ずずれる。**
当初 `daily_records.status` に `incomplete` を持たせようとしたが、
「`clock_in` があり `clock_out` がなく `work_date < 今日`」で打刻列から導出できると気づき、
カラムごと削除した。結果として日次バッチも不要になった。
持たせる前に「これは導出できないか」を一度問うと、状態管理が1段減る。

**設計方針は、書いた直後に具体的な処理と突き合わせないと言葉だけ残る。**
「追記のみ」と書いた10分後に `update`/`delete` する承認処理を書いていた。
方針を書いたら、その方針に反しそうな処理を1つ挙げて検証すると早く矛盾が見つかる。

**Cookie の設計は属性だけでなくオリジン構成とセットで考える。**
`SameSite=Lax` は「クロスサイトの POST に Cookie を送らない」仕様なので、
Vite dev server (`:5173`) から API (`:3000`) を叩く構成では認証が通らない。
逆に同一オリジンに寄せれば、CORS 設定も CSRF トークンも丸ごと不要になる。
Cookie 認証を採用した時点で、オリジン構成が設計事項になる。

**ワークフローの共通部分は申請種別によらない。**
承認 / 却下 / 自己承認禁止 / 承認期限 / 通知は、修正申請でも休暇申請でも同じもの。
ヘッダを分離するかどうかは「申請種別が今後増えるか」で決まり、勤怠では必ず増える
（残業事前申請、直行直帰、出張、シフト変更…）。
逆に種別が増えないドメインなら、分離は過剰になる。

**設計判断は他の箇所の複雑さを減らすことがある。**
変更経路を申請に一本化した副次効果として、`time_entries.source` から `'admin'` が不要になった
（管理者の代理修正も `'correction'` 経由になるため）。
監査ログテーブルも不要になった。1つの判断が2箇所を単純化している。

**学習目的のプロジェクトでは「面倒な部分」を意図的に残す価値がある。**
日跨ぎ勤務、状態遷移、承認トランザクション、楽観ロックは、
省こうと思えば省けるが、省くと学習題材としての密度が落ちる。
どこを簡略化してどこを残すかを、最初に意識的に決めておくとブレない。
